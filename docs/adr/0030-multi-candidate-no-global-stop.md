# 多候选翻页里「整页零新增」不是一条全局闸：队列点完才叫到底

`followPages` 的 `zero-new` 与 `loop` 两闸只在**链式单候选**那侧生效；一次列出多个分页的**多候选**模式下，某一候选页零条目或整页与别页重复，只跳过它自己，队列里其余分页照常抓，`stoppedBy` 停回 `end`。

**为什么**：多候选的语义是「这一页已经把同组各分页列全了」，而这一组里出现与入口页内容相同的页是**常态**——书籍详情页自己就列着第 1 页，翻页规则同时把 `index_1`（重复）与 `index_2…index_N` 一起交出来。把链式那侧的「整页零新增 = 回环/软404」套过来，`break` 掉的是整个循环，于是第一个重复页把后面所有分页一起带走。真机读数（同一批共用一套模板的书源，逐家冷缓存重跑）：笔趣阁 165 章读成 100、神马小说 220 章读成 100、眼小说网 707 章读成 100、第一小说 1839 章读成 100。对面那侧的多候选是逐条全抓、条目最后统一去重，没有这道早停。

**为什么这不是放宽早停**：链式那侧两闸一字未动——一条 `next` 规则顺着往下跟时，「整页零新增」仍然是「到底或软404」的判据（`tests/services/pagination.test.ts` 的「回环（越界页重复首页内容）→ loop 停」与「零新增（空页）→ zero-new 停」两条钉子继续守着这两种停法）。改的只是这两判据的**适用范围**：它们描述的是「下一页」这条链，不描述「同组分页清单」。

被否决的做法：

- **保留早停，另给重复页加一条页数上限或「前 K 页容错」**：那是拿参数冒充判据，K 取几都是猜；而这条判据错了以后，症状是「目录少几十到上千章且不报错」，正是本仓定的最高罪那一类。
- **多候选也判 loop，只是改成 `continue` 并保留 `stoppedBy='loop'`**：`stoppedBy` 是「凭什么判定到底」的读数，多候选把队列点完之后并无回环发生，报 `loop` 会让读的人以为站点在发重复页。
- **在抓取层比对两页正文相同就丢**：为省一次请求引入内容比对，而这里真正要保的是「其余分页必须被抓」——重复页被丢不丢都不影响结论，去重本来已由 keyOf 承担。

**代价**：多候选模式下重复/空页不再提前收手，一轮目录会把规则列出的每个分页都打一遍（页数由规则与 `tocMaxPages` 说了算）。换来的是「少掉的章不靠运气」。

锚点：`src/services/pagination.ts` 的 `followPages`（两闸的适用范围）与 `FollowResult.stoppedBy`（五态读数的家）；`src/services/reading.ts` 的 `followOrSingle`（链式与单页的分岔）；钉子 `tests/services/pagination.test.ts` 的「多候选：某一候选与入口页整页重复 → 其余候选照抓（不得中止整轮）」；矩阵行 `f-toc-paging`（翻页形状）、`g-chapter-boundary-guard`（另一侧不许放松的串章闸）；真机改前/改后逐源读数住在 `f-toc-paging` 的 `note`。
