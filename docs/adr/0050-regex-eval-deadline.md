# 用户正则的求值走 vm 死线：宁可废掉一条规则，不许钉住主线程

Status: accepted

书源规则里的正则是用户写的。一条合法、能编译、却病态的模式（嵌套量词遇上不匹配的长输入）在主线程上是指数级回溯——几十毫秒还是几十分钟，只差几个字符的长度，而插件与宿主同进程，钉住主线程等于让这一进程里所有其他请求与界面一起排队。本仓把**所有**过用户正则的求值收进 `engine/regex-guard.ts`：在 `node:vm` 的上下文里跑，用 vm 脚本执行的超时兜底——超时即抛 `RegexDeadlineError`，不赌回溯的形状与深度。

## 决定

1. **死线随工作量放宽，而不是一个固定数**：基础预算 200ms，每满一 MB 文本追加一档，封顶 1200ms。写死 200ms 会把「大而合法」的整页扫描判成病态——改前是慢但成功，改后变成一条规则错误，那是拿假阴性换稳定。封顶仍在：超过它就不再是「慢」而是「假死」。这条算式只有 `deadlineFor` 一处，调用点不许各自解释「为什么这趟给了 500ms」。
2. **批量口径一趟一次 vm 往返，批内每条独立**：CSS 属性过滤对整批条目用同一条脚本——逐条一趟会把千元素列表变成千次脚本执行，开销吃掉收益。脚本在每次 `test` 前把 `lastIndex` 归零：全局 / 粘滞正则不许跨条目吃匹配（复用游标会把第二、四条读成「不命中」的静默错值）；成功交回时恢复调用前的 `lastIndex`，批量过滤不替调用方推进游标。条目的属性值在**宿主侧**取齐再交给脚本，所以求值窗口内不含宿主回调：超时预算只管正则本身（宿主函数若被请进沙箱就不归它管），共享沙箱被中途覆写这条路也一并堵死。
3. **炸掉的那趟把 `lastIndex` 归零**：超时留下的半截游标会让下一次同一正则从中间起步，读出来是错值而不是错误。成功路径不动它——全局正则 `test` 的推进语义照旧，守卫不许顺手「修正」原生行为。
4. **超时不是空结果**：引擎侧转成带段级定位的 `RuleEvalError`，服务侧转成「这条规则不可用 + 留痕」。`RegexDeadlineError` 自己不带定位——守卫层不知道在评哪一段，定位是调用点的东西；它因此不是 `EngineError` 子类，也不许带着无定位的形状进 HTTP 状态映射（归属裁决写在 `engine/errors.ts`）。

## 被否方案

- **静态黑名单 / 嵌套量词启发式**：嵌套量词本身不是错误，只有配上不匹配的长输入才炸——按形状判死会误杀合法写法，而黑名单永远在追下一个新形状。
- **丢进 worker 线程**：一条规则一次跨线程往返，正文链路每章要跑几十次求值；且引擎的求值语义是同步的（`@js` 完成值、宿主方法面），改异步等于重写调用契约——`ADR-0005` 为同一条理由付过一次代价。
- **只给 `js` 面加超时**：沙箱那一条早就有 `jsTimeoutMs`，但正则无处不在（AllInOne 整页扫描、`##` 替换、CSS 属性过滤、`bookUrlPattern` 嗅探），只守最显眼那一处等于没守。

## 代价

每趟多一次 vm 脚本执行。返回值跨 realm：test / replace / OnlyOne 给原生布尔与字符串，matchAll 与 filter 的数组在 vm realm 里构造——`instanceof Array` 对它不成立（`Array.isArray` 成立），filter 数组里装的仍是宿主原物。消费点因此不许用 realm 相关判据；这条口径写在模块头注释里一次，不在各调用点重述。

锚点：`src/engine/regex-guard.ts` 的 `deadlineFor` 与五条 `vm.Script`；`src/engine/errors.ts` 的 `RegexDeadlineError`；消费点 `src/engine/allinone.ts` / `src/engine/css.ts` / `src/engine/replace.ts` / `src/services/search-face.ts` 的 `startsDetail`；`tests/engine/regex-guard.test.ts`；正文侧的站点可用性读数归 `DSH_CONTENT_AUDIT`（见 `docs/development.md` 的「真链路门控」）。
