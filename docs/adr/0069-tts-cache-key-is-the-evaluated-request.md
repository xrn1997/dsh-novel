# 段音频缓存键取实际请求，不取原始参数

Status: accepted

段音频的缓存键由「引擎标识 + 求值后的实际请求 + 文本」组成：HTTP 源用 `method / url / body`，宿主语音服务用服务身份 + 音色 + 语速；原始速率与音色不再直接进键。请求没变就复用，请求变了才重新合成。背景：最初的键把「引擎 + 模板 + 音色 + 语速 + 文本」原样拼起来，而模板并不消费所有这些参数——内置引擎把语速压到端点能收的整数档，同一档内的两个语速会拼出不同的键、却求值出完全相同的 URL；不消费音色的订阅模板同理。

## 决定

- **HTTP 源先求值再查缓存**：`planTtsRequest` 先产出请求计划，键取 `method / url / body` 与文本；求值失败先于缓存命中，坏配置不能拿旧字节冒充可用。
- **宿主语音服务按参数键**：键取服务身份 + 音色 + 语速 + 文本；服务自身决定这些参数是否真的改变音频。
- **文本仍单独入键**：即使模板不把文本放进 URL / body，不同文本也不能共键。
- **键仍走 JSON 数组编码**：字段之间没有分隔符歧义。

## 后果

- 同一语速档内的两个速率、模板不消费的音色变更，都命中同一段缓存。
- 模板里带时间戳 / 随机数的引擎会因请求每次不同而不再跨请求命中——这是正确方向。
- 旧键条目成为孤儿，按 mtime 轮到后由 LRU 清掉，不需要迁移。

## 被否方案

- 保留原始参数键、另做「同档归一」：归一规则要跟着每个引擎的模板走，等于把引擎语义抄进缓存层。
- 只把 `rate` 归一成端点档位：解决不了音色与未来模板参数。
- 把请求头也放进键：凭据头会随登录态变化，且引擎身份 + URL / body 已覆盖会改变音频的部分。

锚点：`src/services/tts-cache.ts` 的 `ttsCacheKey`；`src/services/tts.ts` 的 `TtsService.synthesize` / `planHttp`；`src/services/tts-request.ts` 的 `planTtsRequest`；`tests/services/tts.test.ts`；`tests/services/tts-cache.test.ts`。
