# 缓存有效性靠「代际 + 槽位」入文件名，不做删除式失效；章名进槽位、URL 不进

两条正交的缺陷要各自挡：「规则变了」与「站点侧目录变了」。

- **代际入文件名**：按引擎面细分的规则指纹 + baseUrl 算出一个代际，**写进缓存文件名**，而不是删除旧缓存。根因是同址替换复用 `sourceId` 保书架引用（见 `docs/adr/0010`），于是「身份没变」被当成了「内容仍有效」，而全仓没有清缓存出口、阅读器也从不发 `refresh=1`，脏命中是永久的。入文件名后，在途请求写的是它起飞时那个代际的文件名，新规则的读永远看不见它——「旧在途写回」自动无害，不需要墓碑也不需要取消通道。指纹**刻意不含** `auth`：登录态刷新会让整源缓存每次登录后全灭。
- **正文槽位 = 代际 + 章名**：正文曾按章序存，站点前面插一章则全体位移，旧文件端给读者的是**另一章**。章名只存在于目录里，所以 `getChapter` 的目录读取必须上移到缓存读取之前；带时效 token 的站点每次刷目录都换 url，故**不含章节 url**。

接受的代价（不是可优化掉的疏忽）：目录缺失（首次或被 LRU 淘汰）时一次章读会退化成一次目录抓取，**热正文缓存不再能单独服务一章**；越界章序现在先抛 `ChapterNotFoundError`，不再可能命中越界旧文件。另两条在册接受：注入脚本的 `book.name` / `author` 取自书架而非规则，所以**改书架书名后旧正文照样命中缓存、吐旧书名**——把书架元数据入槽位会让每次改名全缓存 miss，更糟，记录不修；代际只覆盖规则、不覆盖代码版本。

被否决的方案：① 删除式失效（必须额外挡回写，而入库有两个调用方，任一处忘了调就重新漏）；② `JSON.stringify(rules)` 整体入指纹（赌键序，且改一条只影响搜索面的规则会作废全部阅读缓存）；③ 槽位含章节 url（永不命中）；④ 只靠代际（挡不住站点侧插章）。

看起来矛盾但已写明不矛盾的一处：正文代际同时收目录面字段（正文的输入是目录的产物）——那里排除的是**站点侧** url 抖动，这里是**规则侧**的 url 变更。

锚点：`src/services/cache-epoch.ts`（`rulesEpoch` / `contentSlot` / `EpochImpact` / `FACES_OF`）；`src/services/cache.ts`；`src/services/reading.ts` 的 `getTocInner` / `getChapter` / `bookMirrorOf`；`CONTEXT.md`「缓存代际」「正文槽位」；`tests/services/cache-epoch.test.ts`。
