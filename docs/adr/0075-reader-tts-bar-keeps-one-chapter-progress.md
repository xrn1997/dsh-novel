# 阅读器听书条也只留章内一条进度，段内时间滑杆退场

Status: accepted

听书条底部的两条进度里，段内时间滑杆只回答「这一句念到哪」，却要读者先分辨哪条能拖；听书的位置与导航本来就是段粒度，一条章内段滑杆就够。段内时间滑杆从阅读器条退场，段内定位这项能力随之不做。

## 背景

上一轮把浮窗收成只剩章内一条（`ADR-0074`），段内时间滑杆留在阅读器条，当「段内微调」的唯一入口。实际摆在一起时，条上两条进度同时出现：短的那条是段内时间滑杆，下面整宽的是章内段滑杆。读者要拖之前得先分辨「哪条能拖、拖了会跳到哪」；而条上真正该回答的是「这一章第几段」——段内秒数对这个读数没有贡献。浮窗与听书条是同一件事的两个表面，一边一条不同粒度的进度，也会让「进度条」长出两套解释。

## 决定

- **阅读器听书条只留章内段滑杆**：末行整宽，拖到任意段即起播，空章不渲染；与浮窗的章内进度条同粒度。
- **段内时间滑杆从条上退场**：`SegmentSeek`、`.novel-tts-seek` 一族样式与「本段进度」文案一并删除；没有入口的 `seekWithinParagraph` 也一并删除。
- **段进度读数不删**：浮窗的进度环与章内进度条仍读 `ttsProgress`；条上不再显示 `m:ss` 读数，正文也不再画段内细线（`ADR-0076`）。

## 边界

- 段内 seek 从界面退场。暂停续播仍在段内原地接上——那是播放层的现场，不是用户导航；要从一个长段的中间听起，只能整段跳过去。
- 章内进度条仍是段粒度，不冒充段内计时；它也不回答「整个播放在这一句的哪一秒」。
- 听书位置仍按段落盘，不因这次删减改变；共用位置与听书细节轨的规约见 `ADR-0078`，不因这条进度条的收减改变。

## 代价

长段里想从中间听起时，只能整段跳。把段内定位做成第二条进度条的代价——多一个要解释、要分辨的控件——大于它带来的便利；段内进度已由浮窗的进度环与章内进度条表达，不需要在条上再养一条可拖的轴。

## 被否方案

- **只在阅读器条保留段内时间滑杆**（`ADR-0074` 原样）：两条并排，读者仍要先分辨哪条能拖；这正是要收掉的那件事。
- **把段内时间滑杆调细或缩窄**：问题不在粗细，而在它是另一套粒度；窄条里它更像装饰，比删掉更含糊。
- **保留只读的 `m:ss` 读数**：没有导航能力，只是多一行数字；段内进度已由浮窗的进度环与章内进度条表达。
- **让章内段滑杆兼任段内定位（同一条轴两种刻度）**：同一条控件同时承担段与秒，读者又要先判断当前刻度，等于把两条的困惑收进一条。
