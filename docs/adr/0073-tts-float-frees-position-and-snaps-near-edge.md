# 听书浮窗自由落位，松手时近边吸附

Status: accepted

听书浮窗的位置从「永远贴左右边缘」改成**自由落位**：现场记块中心坐标，拖动两轴跟手，松手时离视口边够近（≤ 24px）的那条边才贴齐，其余停在原地。两个完整形态、进度不撒谎与能力不丢是既有形态决定；形态与密度之后由 `ADR-0079` 改写、展开态尺寸由 `ADR-0080` 接管。本篇换掉的只是「自动贴边」这一条位置规则。

## 背景

此前浮窗取「两个完整形态 + 自动贴边」，理由是贴边最省地方、也最不容易压住正文。代价是位置被规则吃掉：横向拖动被刻意忽略，松手一律按指针落在左/右半屏吸附回边缘，用户没有任何办法把浮窗停在正文中间或某个自己习惯的角落。这个功能叫「浮窗」，却只有一维自由度；用户的诉求是「随意拖」，贴边只该是其中一种想要的结果，而不是唯一可能的结果。

## 决定

- **现场记块中心**：`{ cx, cy, collapsed }`，两轴各自可为 `null` 表示用缺省（横向贴右缘、纵向居中）。记中心不记左上角，换形态时视觉中心不跳，夹取与吸附都只需减半个尺寸。
- **拖动两轴跟手**：每一帧按指针位移落位并夹在视口内，拖动中不做任何吸附——吸附发生在松手那一刻，行为可预测、可钉测试。
- **松手近边吸附**：横轴取左右两侧 gap 较小者，≤ 24px 就贴齐那条边；纵轴同理且两轴独立，因此能落在边角。两侧都不够近就停在原地。
- **`side` 降级为派生值**：不再是现场字段，而是按 `cx` 与视口宽算出的呈现方向，只派生设置弹层往哪边开（左缘镜像）；贴边形态不归它——收掉靠屏幕那一条边框、把那两侧改成直角，归块边缘与视口边算出的 `data-flush`（`deriveMiniBarFlush`）管，块悬在屏内时它是 `none`。视口变化时两个派生随宽度重算。
- **贴着的边在视口变化后继续贴**：上一帧 gap 为 0 的边贴到新视口对应边，自由位置只夹不漂——拉大窗口时贴右缘的浮窗不该悬在半空。
- **尺寸可量则量、量不到用常量**：展开态内容变化会改高度，拿常量算贴底会留一条缝；量不到实际几何（无 DOM 宿主）时回常量，行为网仍可跑。
- **键盘四向移动**：方向键上下左右各移一档（Shift 三档），Home 回缺省位置；不再有「左右方向键换边」这个独立动作——走到另一侧即换边，或拖过去松手。
- **设置面与阅读器条共读同一份行清单**：语速 / 音色 / 音量 / 定时 / 引擎 / 起播章只在 `TtsSettings.tsx` 维护一处，浮窗与阅读器条各自取成品，不抄第二份控件表。
- **全局快捷键不抢阅读器**：Space 播放/暂停、Shift+←/→ 跳段、Esc 收起只在没有阅读器子树且浮窗真在场时安装；阅读器在场时 Space 归滚动、Shift+方向键归选区、Esc 归阅读器浮层契约。

## 边界

- 不做全宽底部坞：`shell.overlay` 推不动宿主布局，通栏形态会压宿主 chrome 与右下状态泳道。
- 不做拖动中磁吸：实时吸附要在吸附瞬间重算拖拽基准，否则来回抖，还要处理两轴阈值竞争，换来的手感提升不值这份复杂度。
- 不避让宿主 chrome 与状态泳道：只保证整块在屏内，落哪由用户定。自由落位的代价就是用户可能把它放在不想放的地方，那由用户再拖开。
- 两个完整形态、进度不撒谎、能力不丢不变；密度与命中档由 `ADR-0079` 改写、展开态尺寸由 `ADR-0080` 接管；在场判据仍归 `ADR-0072`（本决定不碰它）。
- 不记自由左上角：现场是中心 + 收起态 + 展开态宽高（尺寸两轴见 `ADR-0080`），不做「上次的绝对坐标」那种会随视口漂移的存法。

## 被否方案

- **半隐胶囊 + hover 唤醒 / 同一胶囊端头抽屉**：收起态只剩半截或要靠 hover 才补全，触屏没有 hover，收起态无法独立使用；把第二个形态伪装成第一个，用户永远分不清哪一块才是完整控件。
- **340×270 精修媒体卡**：能力齐全但纵向堆叠过多，遮挡远大于控制需要；紧凑边栏用同一组能力换更小的常驻占布。
- **竖签**：省地但换了控件形状，拉出像另一个物件；横胶囊的收起态能直接承接身份与读数。
- **拖动中磁吸**：拖到 24px 内就实时吸过去。吸附瞬间必须重算拖拽基准，否则指针一动就弹回；横纵两轴各自吸附还会互相拉扯。用户感知不出比松手吸附更聪明的地方，实现与测试成本却高出一截。
- **只放开横向的半自由补丁**：保留 `side + anchorY`，另加一个自由横向坐标。位置语义于是同时有两个主人（贴边与自由），圆角镜像、弹层方向、夹取都要伺候两套，迟早再打架。
- **保持贴边不动**：位置被规则吃掉，用户没有任何办法把浮窗停在正文中间或自己习惯的角落——这正是要修的那件事。
